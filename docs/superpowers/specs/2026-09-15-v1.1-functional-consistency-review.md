# V1.1 功能一致性调查归档

> 日期：2026-09-15（2026-09-16 更新）  
> 用途：作为 V1.1 设计逐项核对清单，记录功能语义与文档一致性的核对过程与结论。  
> 状态说明：F01–F13 的核对已全部完成，口径均已确认并回写主设计。其中 F09、F11 的结论性质为实现/部署默认值，需在部署方案确认时最终敲定，不阻塞开发实施。本文只归档核对过程与结论，不替代主设计文档，也不新增已确认需求。

## 0. 核对范围与已确认基线

本次调查仅检查当前方案是否忠实反映此前已经讨论过的功能方向，重点覆盖 Trace 聚合、风险/状态判定、通知、API、日报、HTTPS 和历史兼容。

以下内容视为此前已经确认的方向，不在本文件中重新定义：

- 风险等级使用 `none/low/medium/high`，取消新产生的 `critical`；历史 `critical` 的兼容范围见 F12。
- `high` 表示任务失败或任务中断，需要人工介入；`medium` 表示出现工具错误或长时间循环后仍正常完成任务。
- `incomplete` 是独立的链路完整性状态；仅缺失终止事件且没有循环、调用失败或异常中断证据时，才可判为链路不完整。
- 高风险通知通过现有飞书链路发送；中风险、低风险和无风险不发送即时通知；每条高风险 Trace 只发送一次的具体语义见 F05。
- `/v1/audit-logs` 是供用户的 coding agent 读取已存储日志并批量审计的 API，不承担上游日志写入。
- 首页按 Agent 展示；Agent 页按发起用户聚合，再按 Trace 区分任务；任务详情展示审计结论、证据链和折叠的原始日志。
- 每天发送的全局审计日报继续保留。
- 生产公网日志传输使用 HTTPS；容器内部健康检查可以继续使用 HTTP。

## 1. 调查可信边界

- “`expected_purpose` 未在用户明确提出的三个新增必填字段中出现”只能证明它尚未在已知讨论摘要中得到明确确认，**不能证明用户已经拒绝该字段**。
- `medium` 的讨论原话是“工具出错或出现长时间循环后还能正常完成任务”。不能把任意重试、任意超时或任意异常自动归为中风险；具体哪些情况满足“还能正常完成”仍需结合终态判断。
- 上一轮 Dashboard 调查段落一方面把“已完成但有异常”归给 `incomplete + none/low`，另一方面又说这类任务统一进入“待确认”，存在自相矛盾。该段不作为结论，已依赖 F01 核对后处理。
- 使用编码后的游标可以避免分隔符歧义，但编码本身不保证动态写入期间分页稳定；稳定性仍取决于排序键、快照/水印和查询条件。
- 一条 Outbox 记录不等于系统已经具备“更新同一卡片”的能力；现有代码是否支持飞书卡片更新、更新接口和失败重试，已在 F05 单独核对。

### F01：`incomplete + medium` 与中断判定规则

- 当前文档位置：
  - [任务级日志字段与风险说明](2026-09-14-v1.1-audit-task-review-design.md#4-任务级日志字段)
  - [Trace 生命周期与结论收敛](2026-09-14-v1.1-audit-task-review-design.md#53-生命周期与完成判定)
  - [状态判定优先级](2026-09-14-v1.1-audit-task-review-design.md#63-状态判定优先级与边界场景)
  - [验收用例](2026-09-14-v1.1-audit-task-review-design.md#141-任务和风险)
- 当前文档/代码事实：主设计的验收段曾列出 `incomplete + medium`，并要求其派生为 `resolved`；同时又规定缺终止事件且存在失败/循环证据时为 `interrupted/failed + high`，并将 `incomplete + high` 列为非法组合。
- 与此前讨论的关系：此前确认“只有缺失终止事件且链路正常才是 `incomplete`；有循环、调用失败或异常中断证据就是任务中断”。本次进一步明确：日志审计是后审行为，日志发送完成并开始审计时，任务已经结束；审计不能再让 Agent 判断未来是否能够恢复。
- 已确认的功能口径：是否“恢复”必须由已经发送的完整日志中的实际终止结果确定，不是 LLM 对未来的推测。只有日志中已经出现明确成功终止事件，并且此前出现过工具错误或长循环后最终完成，才允许判定为 `success + medium`。缺少终止事件且存在循环、调用失败或异常中断证据，直接判定为 `interrupted + high`；缺少终止事件且链路正常，判定为 `incomplete`。
- 影响：`incomplete + medium` 不再是“LLM 判断可恢复”的兜底组合；保留它会把后审结论错误地建立在未来推测上，并影响人工介入、页面行动状态和飞书通知。
- 回写主设计的内容：删除 `incomplete + medium` 合法终态及相关验收用例；同步修订状态判定、`action_state`、Dashboard 文案和通知条件。`incomplete` 的风险等级和页面文案见 F08。
- 状态：**已确认并回写主设计**。

### F02：复合 Trace 键与单 `trace_id` URL

- 当前文档位置：
  - [Trace 主表](2026-09-14-v1.1-audit-task-review-design.md#51-trace-主表)
  - [事件关联键](2026-09-14-v1.1-audit-task-review-design.md#52-事件关联新增列与扫描游标)
  - [通知与 Dashboard](2026-09-14-v1.1-audit-task-review-design.md#10-高风险飞书通知)
  - [Dashboard 原型](2026-09-14-v1.1-audit-task-review-design.md#1254-页面线框与视觉稿)
- 当前文档/代码事实：数据库主键定义为 `(agent_id, trace_id)`，但调查发现页面或卡片链接存在只使用 `trace_id` 的写法。通知去重键则包含 `agent_id` 和 `trace_id`。
- 影响：不同 Agent 使用同名 `trace_id` 时，单 `trace_id` URL 无法唯一定位任务，可能打开错误 Trace 或无法生成确定链接。
- 已确认的功能口径：不要求 `trace_id` 全局唯一，Trace 的业务唯一键固定为 `(agent_id, trace_id)`。Dashboard、飞书卡片和 API 的 Trace 级定位都必须同时携带 `agent_id` 与 `trace_id`；不新增 `trace_key`。
- 回写主设计的内容：统一使用 `/dashboard/agents/{agent_id}/traces/{trace_id}` 形式的 Trace 详情路径；路径参数必须进行 URL 编码。API 响应始终返回两个字段，精确查询支持两个字段组合。
- 状态：**已确认并回写主设计**。

### F03：API 游标示例与定义、返回粒度不足

- 当前文档位置：
  - [读取 API 契约](2026-09-14-v1.1-audit-task-review-design.md#11-coding-agent-批量读取-api)
  - [扫描游标](2026-09-14-v1.1-audit-task-review-design.md#52-事件关联新增列与扫描游标)
- 当前文档/代码事实：设计定义了 Trace 列表稳定排序和游标字段，但示例形如 `时间|10231`，与文字定义 `last_event_at|agent_id|trace_id` 无法对应；同时 API 契约写成默认不返回全量事件，`include_events=true` 时只返回采样事件。
- 已确认的功能口径：API 返回粒度必须与 Dashboard 一致。每条 Trace 返回完整任务上下文、审计结果、证据引用、全量事件以及每个事件的完整 `raw_json`。coding agent 拿到的是与页面同源的审计材料，不需要靠摘要字段自行推断缺失证据。
- 已确认的边界：`maxEventsPerTrace` 只限制 LLM 送审输入，不限制 API 和 Dashboard 的日志返回。审查输入是否发生采样只影响结论的置信说明，必须单独标记，不能把 LLM 采样结果当成 API 日志的截断。
- 已确认的分页口径：API 以 Trace 为分页对象；游标由服务端生成，客户端只原样回传，不需要理解或自行拼接。游标定义与示例统一包含 `last_event_at`、`agent_id`、`trace_id`，对外可使用 URL-safe 编码的结构化对象。编码只解决表达和分隔符歧义，不单独证明持续写入场景下的分页稳定。
- 补充确认（响应体有界）：不引入 `include_events` 之类的裁剪开关，改由游标分页本身收敛体积——`limit` 定义为上限而非保证，累计响应字节触顶时提前收尾、少返若干条并照常返回 `next_cursor`。客户端原样回传游标即可续读，不丢行、不重复。
- 影响：摘要或采样返回会让 coding agent 的信息粒度低于 Dashboard，无法基于同一份证据批量审计；游标示例与定义不一致会让实现方把事件 ID、水印和 Trace 复合键混用，造成分页重复或漏项。
- 回写主设计的内容：API 段落改为返回完整事件与 `raw_json`；删除“默认不返回全量事件”和“返回采样事件”规则；把采样标记限定为 LLM 审查输入元数据；统一 11.1 的游标示例与定义并补充响应体字节上限；同步 11.2、12.1 影响矩阵和 14.3 验收。
- 状态：**已确认并回写主设计**。

### F04：`expected_purpose` 额外必填

- 当前文档位置：
  - [任务级日志字段](2026-09-14-v1.1-audit-task-review-design.md#4-任务级日志字段)
  - [字段校验与脱敏](2026-09-14-v1.1-audit-task-review-design.md#8-字段接收校验与脱敏)
- 当前文档/代码事实：主设计曾将 `requester_id`、`original_request`、`expected_purpose`、`agent_result` 都写入字段契约，并将 `expected_purpose` 作为 `run.start` 必填字段；用户此前明确提出的新增必需字段是“发起用户”“用户原始请求”“agent 执行结果”三个字段。
- 影响：如果 `expected_purpose` 未被确认却作为 strict 模式必填，会扩大上游 Agent 改造范围，并可能使原本可审计的日志被接入层拒绝。
- 已确认的功能口径：V1.1 必填任务级字段只有 `requester_id`、`original_request`、`agent_result` 三个。`expected_purpose` 保留为可选增强字段，理由是现有规范已通过 `run.start` 的任务目标和 `llm_intent.input` 承载同类信息，V1.1 不要求所有上游 Agent 为此改造。
- 补充确认（论证闭环）：上述“可选”的论证依赖 `llm_intent` 能进入审查，而 7.1 的送审字段白名单原本未包含它、且明令“其他字段不得进入 Prompt”，会使论证被架空。已确认把 `llm_intent` 的 `input`/`output` 加入 7.1 白名单（代码中已落库为 `llm_intent_json`，`llmReviewer` 已有 `sanitizeFreeText` 做 500 字截断），而非修改论证。
- 回写主设计的内容：字段定义、8.1 约束表、8.2 strict 模式拒绝范围、5.6 回填的 `context_status` 判定、7.1 输入白名单、12.1 影响矩阵和 14.6 验收均改为三必填 + 一可选；接入指南和日志规范对比表同步修订。
- 状态：**已确认并回写主设计**。

### F05：“同卡片更新”是否属于一次通知语义

- 当前文档位置：
  - [高风险通知去重](2026-09-14-v1.1-audit-task-review-design.md#101-一条-trace-一次通知)
  - [通知验收](2026-09-14-v1.1-audit-task-review-design.md#142-通知)
- 需求边界：用户确认的需求只有“高风险 Trace 发送一次飞书卡片通知”，从未提出卡片更新。卡片更新是上一轮设计为了兼容“后续新增高风险证据”而自行扩展出来的能力，不属于 V1.1 需求。
- 代码事实：现有发送链路是群自定义机器人 Webhook（`src/adapters/delivery/feishuBotClient.js`，`/open-apis/bot/v2/hook/`），发送成功后只返回 `{ mode: 'live', delivered: true }`，不保存 `message_id`，全链路没有卡片更新调用。飞书卡片更新走应用身份与 `im` 权限，是另一套接入方式。
- 场景溯源：主设计 10.1 原始表述针对的是旧时间窗口模型——同一 Trace 被多个 30 分钟窗口切片段重复审查，每个窗口可能发现新的高风险 Finding，导致去重键变化并重复告警。V1.1 改为整条 Trace 一次性审查后，该场景不再存在。
- 已确认的功能口径：V1.1 不提供卡片更新能力。审计单位和通知单位都是整条 Trace，一条高风险 Trace 只发送一张卡片；后续新增证据只写入数据库，在任务详情页和读取 API 中可见。去重键作用是防止同一次判定的重复投递（重试、重启、并发调度），不是处理后续证据。
- 补充确认（去重键与分片）：去重键沿用现有 `dedupeIdentity` 的哈希写法（`feishu_trace_alert:` + sha256(`[agent_id, trace_id]`) 前 24 位），不使用明文冒号拼接——明文拼接下 `agent_id="a:b"/trace_id="c"` 与 `agent_id="a"/trace_id="b:c"` 会碰撞。同时取消卡片分片：Trace 模型下一张卡片只承载一条结论（发起人、请求、目的、结果、风险原因、一个链接），远低于 19 KiB 上限，分片是旧模型“一张卡塞 N 条 Finding”的遗留；超长直接截断，完整证据由 Dashboard 链接承载。取消分片后“一条 Trace = 一条 Outbox 记录 = 一张卡”自然成立，无需改动 `outboxStore` 与 `eventPublisher` 的投递语义。
- 回写主设计的内容：10.1 改写为“一条 Trace 一次通知”并删除分片相关表述、6.3.3 固化规则、12.1 影响矩阵、14.2 验收用例。
- 状态：**已确认并回写主设计**。

### F06：超时、稳定事件数、单 Trace 事件数默认值

- 当前文档位置：
  - [Trace 封存规则](2026-09-14-v1.1-audit-task-review-design.md#53-生命周期与完成判定)
  - [事件截断策略](2026-09-14-v1.1-audit-task-review-design.md#55-单-trace-事件上限与截断策略)
  - [保留策略](2026-09-14-v1.1-audit-task-review-design.md#57-保留策略)
- 当前文档/代码事实：设计写入了 `waitingUserTimeoutMinutes=1440`、`idleTimeoutMinutes=60`、`minStableEventCount=2`、`maxEventsPerTrace=2000` 等具体默认值，且未区分哪些是产品规则、哪些是可调初始值。
- 影响：如果后续实现把这些数值当成已确认产品规则，可能错误判定长任务、等待用户任务、迟到事件和超大 Trace；事件截断还会影响 LLM 证据完整性。
- 已确认的功能口径：
  - **`run.waiting_user` 超时不再判 `high`**。用户长时间未回复自己的 Agent 属于正常等待，不是异常中断；按原规则会对每一批超时等待任务发出“需要人工介入”的飞书告警，是误报主来源。删除 6.3.1 原规则 4，使其自然落入规则 6 的 `incomplete + none`，页面显示“待确认”。
  - **封存优先级必须补排除条件**。原表中优先级 2（等待用户超 `waitingUserTimeoutMinutes`）被优先级 3（最后事件早于 `idleTimeoutMinutes`）抢先命中，1440 分钟阈值永远不可达。优先级 3 增加“且最后一跳不是 `run.waiting_user`”。`sealed_reason='waiting_user_timeout'` 保留，用于排障时区分“用户没回”与“链路断了”。
  - **`minStableEventCount` 整条删除**。5.3 已规定未封存 Trace 不出结论，即审查只发生在封存之后；封存意味着不会再有新数据，此时再要求最少事件数没有意义，只会让仅含孤立 `run.start` 的 Trace 永远送不进审查。改为“封存即送审”。
  - **`maxEventsPerTrace=2000` 保留，但采样规则改为按优先级填预算制**。原规则 3“保留每个 `span_id` 的首末事件”在 span 数量大时其保留集本身即可超限，而规则 4 只管“其余”，无二次裁剪约定。改为按优先级依次填充预算，填满即停，最低优先级桶内按 `ts, id` 确定性丢弃，使规则同时完备且确定。
  - **保留期改为 Trace 单位**：已封存 Trace 及其全部事件保留 30 天，`risk_level=high` 的 Trace 保留 90 天（与现有 `llmUsageDays: 90` 同档），每 Agent 上限 2000 条 Trace 作为容量安全阀。依据：实测单条事件 `raw_json` 平均 309 字节、最大 377 字节，含其余列与索引开销后单行约 700 B–1 KB，日均 1 万条事件时 30 天约 300 MB，SQLite 无压力；下限由功能决定——“待确认”状态要求真人回来确认结果，保留期必须覆盖跨周末与假期的响应周期，7 天为绝对下限、14 天为舒适下限，30 天同时覆盖一个自然月的复盘周期。
- 关键实施约束：现有 `config.json` 的 `eventsHours: 48` 与 `maxEventsPerAgent: 200` **必须删除，不能与新配置并存**——两套规则同时生效时 48 小时会先赢，Trace 保留期形同虚设，且每 Agent 仅留 200 条事件的配额会在 Trace 封存前裁掉证据，使 `evidence_event_ids` 指向已删除的行。另需补一条孤儿事件清扫：无对应 `audit_traces` 行的事件按同样天数单独清理，否则会永久累积。
- 补充确认（保留守卫的失败出口）："未封存或未审查的 Trace 不按年龄删除"守卫的"天然自限"论证只覆盖封存不积压，未覆盖审查失败不积压——LLM 持续失败的 Trace `review_version` 永远为 0 且非 `backfill`，会被永久保留。已确认出口：重试计数持久化为 `audit_traces.review_retry_count`（失败递增、成功归零），`maxInvalidOutputRetries` 耗尽后该 Trace 按 `traceDays` 正常清理，清理前计入 `/health` 的"审查失败待清理"计数。
- 回写主设计的内容：5.3 封存表与送审门槛、5.5 采样规则、5.7 保留策略整段重写、6.3.1 删除原规则 4、12.1 与 14 章同步；主设计新增“配置默认值性质表”，逐项标注每个数值属于**产品规则**还是**可调初始值**，避免实现者把 1440 分钟一类数值当成不可动的产品约定。
- 状态：**已确认并回写主设计**。

### F12：历史 `critical` 兼容范围

- 影响：如果迁移时直接删除 `critical`，历史详情、日报统计、通知去重或旧 API 可能无法读取；如果新页面继续展示 `critical`，又会违背新的风险等级模型。

  - 历史数据**只在读取层映射**为 `high`，**不做物理回填**，旧日报不重新计算，旧通知记录不迁移。

## 4. 复核后仍然一致的方向

以下方向经本轮逐项核对后仍然成立，可作为实施期的检查基线：

- 新增三个用户明确要求的任务字段：发起用户（`requester_id`）、用户原始请求（`original_request`）、Agent 执行结果（`agent_result`）；`expected_purpose` 为可选增强字段（F04）。
- Trace 作为审计聚合单位，Finding 不承载 Trace 的唯一结论。
- 高风险代表需要人工介入；中低风险和无风险不发送即时飞书通知。
- 仅高风险 Trace 触发即时通知，一条 Trace 一张卡片、不更新、不分片（F05）；每日全局审计日报继续发送。
- `/v1/audit-logs` 是读取 API，供 coding agent 批量获取已存储日志，返回粒度与 Dashboard 同源（F03）。
- 前端按 Agent → 发起用户 → Trace 任务 → 详情分层；详情保留审计结果、证据链和折叠原始日志。
- 公网日志传输使用 HTTPS，容器内部健康检查不因此必须改为 HTTPS（F11）。

本轮核对后被推翻或细化的部分：

- `action_state` 由三值扩为**五值**，改按 `sealed_at` 与 `review_version` 两个显式轴派生，新增“进行中”与“未审查”（F08）。
- `run.waiting_user` 超时**不再判 `high`**，改判“待确认”（F06）。
- 保留策略由事件单位改为 **Trace 单位**：30 天 / 高风险 90 天 / 每 Agent 2000 条 Trace；现有 `eventsHours: 48` 与 `maxEventsPerAgent: 200` 必须删除（F06）。
- 历史数据**不做 LLM 审查**，回填即封存并保持“未审查”状态（F12）。
- `/query` **不加鉴权**，定位为开发测试用途（F10）。
